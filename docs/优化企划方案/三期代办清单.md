## 第 2 步：数据库 schema 规范化（约 3–5 天）→ R9

- [ ] 2.2 编写迁移脚本：读取旧 dev.db，解析 JSON 字段写入新表；校验迁移前后记录数与字段值一致
- [ ] 2.3 更新 `battles.ts` 读写逻辑与 Zod schema；更新前端 DTO 解析（client.ts 去掉 JSON.parse 兼容层前保留一个版本的兼容）
- [ ] 2.4 后端测试同步更新（利用一期建立的 battles.test.ts 骨架）
- [ ] 2.5 验证：旧库迁移零丢失；PostgreSQL 切换演练成功（改 provider + DATABASE_URL + db push）

## 第 3 步：弹道模型升级（约 3–5 天）

- [ ] 3.1 `lib/ballistics.ts` 新增 RK4 数值积分弹道（含空气阻力模型 + 弹道系数表查表），保留旧模型作为对照
- [ ] 3.2 增加弹道系数表数据（`data/` 下），按弹种配置
- [ ] 3.3 对照测试：0–1500m 新旧模型偏差 ≤ 3°；1500–2500m 新模型增加锚点测试（查表基准值）
- [ ] 3.4 切换默认模型，旧模型保留一个版本后删除；更新头注适用范围说明
- [ ] 3.5 验证：`npm.cmd test` 全绿；3D 弹道轨迹视觉回归（截图对比）

## 第 4 步：部署形态完善（约 1–2 天）→ R9

- [ ] 4.1 编写 `docker-compose.yml`：frontend（nginx 静态）+ backend（node）+ 可选 postgres 服务
- [ ] 4.2 backend 加 `Dockerfile`；frontend 加 `Dockerfile`（多阶段：构建 → nginx）
- [ ] 4.3 补 `.env.example` 模板；README 增加 Docker 启动章节
- [ ] 4.4 验收：`docker compose up` 一条命令拉起，冒烟通过（打开页面 → 开火 → 保存 → 机库可见）

## 第 5 步：E2E 测试体系（约 3–5 天）

- [ ] 5.1 引入 Playwright（装在根目录或 frontend devDeps，npm 安装）
- [ ] 5.2 核心旅程用例 ≥ 5 条：① 首页加载 ② 选弹→3D 点击开火→分析窗口出现 ③ 跳弹场景文案 ④ 结束战斗保存→机库列表出现记录 ⑤ 机库回看命中详情
- [ ] 5.3 纳入 CI（独立 job，容器内起前后端 + 无头浏览器）
- [ ] 5.4 沿用 verify-*.png 规范输出每步截图，失败时自动留存
- [ ] 5.5 验收：CI 中 E2E job 全绿；本地 `npx playwright test` 可复跑

## 第 6 步：观测性建设（约 2–3 天）

- [ ] 6.1 后端接入 pino 结构化日志（请求日志 + 错误堆栈），替换现有 `console.error`
- [ ] 6.2 前端 ErrorBoundary 增加错误上报钩子（本地原型可先落 localStorage/控制台结构化输出）

- [ ] 6.4 验证：debug 模式下一次命中的每步中间值与 `lib/` 单测预期一致
